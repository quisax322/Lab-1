# Ember — Lab 02 «Біти не брешуть», Standard

Навчальна 8-бітна машина на C++17: пам'ять на 4096 байтів, регістри A/B,
лічильник PC, ALU та прапорці Z/N/C. Реалізовано основну стежку M1–M4.

Джерела контрактів:
[умова Lab 02](https://github.com/rmalkevy/Programming-Practice-Projects/blob/main/courses/programming-fundamentals/lab-02-bits-dont-lie.md),
[ISA](https://github.com/rmalkevy/Programming-Practice-Projects/blob/main/courses/programming-fundamentals/ISA.uk.md),
[офіційна перевірка](https://github.com/rmalkevy/Programming-Practice-Projects/blob/main/courses/programming-fundamentals/checks/lab-02.txt).
`src/cpu.hpp` дослівно взято з наданого в актуальній умові блоку, без зміни полів,
типів, початкових значень, констант і сигнатур. `decode()` — внутрішня функція
`cpu.cpp`, тому наданий заголовок не потребує доповнень.

## Збірка й запуск

Windows, PowerShell, встановлена Visual Studio 18 2026 (x64):

```powershell

$ctest = Join-Path (Split-Path $cmake) 'ctest.exe'

```

Якщо CMake доступний у PATH, можна використовувати `cmake` та `ctest` без
повних шляхів. Для GCC/Clang на Linux/macOS:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
ctest --test-dir build --output-on-failure
./build/ember
```

Попередження є помилками: MSVC `/W4 /WX`, GCC/Clang `-Wall -Wextra -Werror`.
У Debug MSVC увімкнено AddressSanitizer; його DLL копіюється поруч із програмою.
Опція `-DEMBER_MSVC_ASAN=OFF` дозволяє збірку без ASan, якщо відповідний компонент
Visual Studio не встановлено. GCC/Clang Debug отримує ASan і UBSan.
MSVC не підтримує UBSan, тому його запуск на цій Windows-машині не заявляється.
Фактично перевірено MSVC 19.51.36260, CMake 4.3.1, Windows x64 Debug з ASan.

а інструкція `INC A` змінює регістр A та Z/N. Новий запуск програми скидає CPU
й пам'ять; після HALT продовження через `step` не дозволено.

## M1 — як працює ALU

ALU отримує один або два байти, повертає байт результату й оновлює `Flags&`.
`Byte` — це `std::uint8_t`: після обчислення лишаються молодші 8 бітів,
тобто результат за модулем 256. Проміжну суму зберігаємо в `uint16_t`, щоб
не загубити дев'ятий біт до перевірки перенесення. Проміжні цілі обчислення
в усіх операціях залишаються в допустимому діапазоні C++.

- Z = 1, якщо вже загорнутий результат дорівнює нулю.
- N = 1, якщо `(result & 0x80u) != 0`: сьомий біт дорівнює одиниці.
- ADD: C = 1, якщо сума більша за 255.
- SUB: C = 1, якщо A < B, тобто потрібна позика.
- SHL/SHR: C отримує старий біт 7/0 відповідно. Зсув завжди на один біт.
- AND/OR/XOR/NOT скидають C у 0.
- INC/DEC оновлюють лише Z/N і зберігають попереднє C, навіть при загортанні.

N показує біт результату, а C — факт перенесення, позики або виходу біта.
Це різні речі: `127 + 1 = 128` дає N=1, C=0. Окремого прапорця знакового
переповнення V в цьому контракті немає.

Приклад 1, обов'язковий: **200 + 100**.

```text
  11001000  (200)
+ 01100100  (100)
-----------
1 00101100  (300 = 256 + 44)
```

Зберігається `00101100`, тобто A=44 (0x2C). Дев'ятий біт означає C=1.
Результат ненульовий, його біт 7 нульовий: Z=0, N=0.

Приклад 2, власний: **255 + 1**.

```text
  11111111  (255)
+ 00000001  (1)
-----------
1 00000000  (256 = 256 + 0)
```

У байті лишається A=0: Z=1, N=0, C=1. Це саме ADD; `INC A` також дасть 0,
але збереже попереднє C за своїм окремим контрактом.

Запуск `build/Debug/ember_tests.exe` друкує приклади M1:

```text
ADD 200 100: result=44  Z=0 N=0 C=1
AND 7 1: result=1  Z=0 N=0 C=0
SHL 128: result=0  Z=1 N=0 C=1
PASS: 2646040 checks
```

## M2 — офіційна перевірка

У батьківській теці був старий `checks/lab-02.txt` із `LOADI` та `run`.
Він не відповідає актуальній Lab 02. У проєкт збережено актуальний файл GitHub
як `checks/lab-02.txt`; батьківський файл не змінено. Реалізовувати Lab 03/04
для старого сценарію не потрібно.

```powershell
Get-Content .\checks\lab-02.txt | .\build\Debug\ember.exe
```

Його стан до обчислення: `PC=0 A=200 B=100 Z=0 N=0 C=0`.
Після ADD: `PC=1 A=44 B=100 Z=0 N=0 C=1`.
Після HALT: `PC=2 A=44 B=100 Z=0 N=0 C=1`.
Наступний `step` друкує `halted` і нічого не змінює.
HALT займає один байт і теж збільшує PC на 1, перш ніж машина залишається
зупиненою. NOP зберігає регістри й прапорці та збільшує PC на 1.

## M3 — програми, які видно

Вимаганий приклад `A=7, B=1`, `[AND, HALT]` є у `checks/lab-02-and.txt`.
Після двох кроків: `PC=2 A=1 B=1 Z=0 N=0 C=0`.

Власна програма містить три ALU-інструкції та HALT. Введіть у свіжому запуску:

set 2 0x18
set 3 0x00
set 4 0x19

regs
step
regs
step
regs
step
regs
step

| PC до | mem[PC] | Дія | PC після | A після | Z | N | C |
|---:|---|---|---:|---:|---:|---:|---:|
| 0 | 0x16 | SHL: 64 * 2 | 1 | 128 | 0 | 1 | 0 |

## M4 — розбір маскою та зсувом

`decode(Byte op)` у `cpu.cpp` повертає два поля:

```cpp
group = (op >> 4) & 0x0F;
index = op & 0x0F;
```

Наприклад, 0x16 = `0001 0110`: група 1 (ALU), індекс 6 (SHL).
Зовнішній `switch` обирає групу, внутрішній — операцію. Для індексів case
використовуємо надані константи опкодів із маскою `0x0F`.
Усі реалізовані інструкції однобайтові, тому наприкінці успішного кроку PC += 1.
Для невідомих опкодів збережено поведінку наданого каркаса Lab 02: як NOP.
Це не означає реалізацію майбутніх інструкцій.

Демонстрація пастки пріоритету: нехай `x=2`, `MASK=1`.
`x & MASK == 0` читається як `x & (MASK == 0)` і дає 0 (false).
Правильне `(x & MASK) == 0` дає true: молодший біт у 2 справді нульовий.
Дужки в перевірках масок у коді обов'язкові.

## Реалізовані опкоди ISA

| Опкод | Мнемоніка | Байти | Вплив на прапорці |
|---|---|---:|---|
| 0x00 | HALT | 1 | Без змін |
| 0x01 | NOP | 1 | Без змін |
| 0x10 | ADD A, B | 1 | Z N C |
| 0x11 | SUB A, B | 1 | Z N C (позика) |
| 0x12 | AND A, B | 1 | Z N, C=0 |
| 0x13 | OR A, B | 1 | Z N, C=0 |
| 0x14 | XOR A, B | 1 | Z N, C=0 |
| 0x15 | NOT A | 1 | Z N, C=0 |
| 0x16 | SHL A | 1 | Z N C (старий біт 7) |
| 0x17 | SHR A | 1 | Z N C (старий біт 0) |
| 0x18 | INC A | 1 | Z N, C зберігається |
| 0x19 | DEC A | 1 | Z N, C зберігається |

Власних розширень ISA немає. LOADI, CMP, MUL, run та інші майбутні завдання
не реалізовано. Команди консолі `set`, `reg`, `regs`, `inc`, `step` — це
керування емулятором з хоста, а не додаткові опкоди гостьової машини.

Debug-збірка MSVC x64 з ASan успішна; попереджень і повідомлень ASan немає.

  скидання старого C логічними операціями й збереження C через INC/DEC.
  Також перевірено всі 256 опкодів з вісьмома початковими наборами прапорців,
  повторний HALT, останню адресу пам'яті та всі початкові нульові байти.

- `lab-02`: актуальні офіційні команди без змін.
- `lab-02-and`: вимаганий приклад AND/HALT.
- `lab-02-trace`: SHL/SHL/INC/HALT і відмова виконати наступний DEC.
- `lab-02-input`: некоректний ввід, межі пам'яті, hex-регістр, DEC, HALT,

## П'ять хвилин для захисту

**0:00–1:00. Машина.** «У пам'яті зберігаються байти команд. A і B містять
числа, PC — адресу наступної команди. `step` читає байт, розбирає його,
виконує операцію та пересуває PC. HALT завершує виконання, наступний step
не змінює стан».

**1:00–2:00. ALU та прапорці.** «ALU рахує над байтами. У 200+100 сума 300,
але в A вміщується 44, а втрачений дев'ятий біт видно через C=1. Z означає
нуль, N — одиницю у старшому біті. Після SUB C означає позику. Після INC/DEC
C залишається попереднім». Покажіть також 255+1 і відмінність від INC.

**2:00–3:00. Біти й маски.** «Одна hex-цифра — чотири біти. 0xA3 — це
10100011, тобто 10*16+3=163. Для 0x16 зсувом вправо й маскою дістаємо групу 1,
окремою маскою — індекс 6». Для біта з номером 3 (нумерація від нуля):
виставити `x |= (1u << 3)`, скинути `x &= ~(1u << 3)`, перевірити
`(x & (1u << 3)) != 0`. Поясніть пастку пріоритету на x=2, MASK=1.

**3:00–4:00. Трасування.** Пройдіть таблицю 64 -> 128 -> 0 -> 1.
На першому SHL з'являється N, на другому — C і Z, після INC C зберігається.
HALT пересуває PC до 4, наступний step залишає його там. Покажіть роботу
командами з `checks/lab-02-trace.txt` і звірте передбачення з `regs`.

**4:00–5:00. Типи й перевірка.** «0xFF — один набір бітів: беззнаково це 255,
а у 8-бітному доповняльному коді це -1, бо 255-256=-1. Компактний байт опкода
зручно зберігати, читати й розбирати на поля. Правильність перевірена
офіційним сценарієм і граничними випадками; HALT не дозволяє виконати DEC
після зупинки».

Можливі зміни викладача: якщо прибрати загортання, байт однаково звузиться
при записі в A, але обчислений надто пізно C буде втрачено; якщо збільшувати
PC на 2, пропуститься наступна команда; якщо перевіряти C у SHL після зсуву,
читатиметься вже інший біт. У майбутній ISA `LOADI A, 0` не встановлює Z:
`JZ` читатиме старе Z й стрибне лише якщо воно вже було 1.
